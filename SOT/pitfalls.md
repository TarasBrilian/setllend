# Pitfalls

## Contract

- **Always check `env::predecessor_account_id() == "intents.near"`** in `mt_on_transfer` and `on_auth`, and whitelist accepted `token_ids`. Never trust a token or sender without checking. Fake-collateral attacks are a known lending exploit class.
- **In `mt_on_transfer`, the fund owner is `sender_id`** (the user who signed the `transfer`), not `intents.near`.
- **Invalid input in `mt_on_transfer`:** panic or return the refund amount. A panic reverts our state and `intents.near` refunds the full amount 📄. Never return a "no refund" value after partially failing.
- **`auth_call` is detached:** the user's intent batch succeeds even if `on_auth` fails. The relayer must read the `on_auth` receipt outcome before telling the user it worked.
- **Never accept deposits via `ft_withdraw` + `msg`:** no refund on failure.
- **`mt_transfer` payouts to `intents.near` are async** and need exactly 1 yoctoNEAR attached 📄. Use a callback and re-credit the internal balance on failure.
- **A `transfer` intent can carry several tokens.** `borrow` and `add_collateral` accept several collateral tokens (D48); `lend`, `repay`, and `liquidate` reject anything but exactly one debt token. Reject a token listed twice, and return one refund per token.
- **300 Tgas limit** per transaction: cap fills per `match_orders`.
- **Storage staking:** every stored order locks NEAR, paid by the contract. Release storage when an order, loan, or note entry closes. Watch the contract's NEAR balance and top it up. Users are not limited (D24), so dust-order griefing is an accepted hackathon risk.
- **Keep NEAR above storage, or a failed payout loses its record (D38).** `on_payout` writes a new free-balance entry when a payout fails. If the contract can't pay for that storage, the callback fails, and the order, balance, or pool was already reduced in the earlier receipt: the tokens stay in Setllend's Intents balance with no record of whose they are (recoverable only by reading the logs and upgrading, D23). The keeper alerts when the contract's free NEAR (balance minus `storage_usage` × byte cost) runs low, and we top it up first.
- **Deploy and init in one transaction.** `new` is `#[private]`, so only the contract account can call it, but deploying with a separate init still leaves an uninitialized contract on chain. Use `cargo near deploy` with the init call. Since D53 the contract starts with no collateral tokens, so put `add_maturity` for each maturity and `add_collateral_token` for each token in the same transaction too: several function-call actions to the contract account itself, after `DeployContract` and `new` (built with `near-api-js`, since `cargo near deploy` adds only the init call ⚠️ check before deploying). BTC goes in only once open question #10 (its bridge exit) is tested; the owner can add it later.
- **Note share math rounds against the acting account** (mint and move round down, burn rounds up), so other holders are never diluted. See [contract-interface.md](contract-interface.md#note-accounting).
- **Simple liquidation:** the liquidator pays the debt in USDC and receives collateral plus a bonus. No DEX swap inside the contract.
- **Oracle callbacks re-validate state.** See [oracle.md](oracle.md#integration-pattern-in-the-contract).
- **Owner parameter updates hit open loans (D50):** `update_collateral_token` applies at once, so lowering a token's liquidation threshold can make loans liquidatable in the same block. The README discloses it, and the keeper picks such loans up on its next scan.
- **Value math overflows `u128` with 24-decimal tokens (D53):** a NEAR amount in yoctoNEAR times a price passes `u128::MAX` around 1 million NEAR. Collateral value and seizure use 512-bit intermediates; the TypeScript mirror uses `bigint`, which has no limit, so it must not round where the contract doesn't.
- **Freezing a token removes its borrowing power at once (D53):** a loan backed only by a frozen token can't borrow more or withdraw any collateral while it has debt, until it repays or adds another token. Its health is unaffected.

## Off-chain

- **Event sources have rate limits that change.** Free FastNear neardata allowed 180 requests per minute in its README but answered 30 blocks per minute on 2026-11-04, too few to follow mainnet, so the backend reads events from the FastNear explorer instead (D55). Its limit is undocumented (about 30 requests per minute passed); the follower stays at 25 and backs off on a 429. If `/health` shows a growing lag, check the explorer's limit first. The books stay correct either way, since they are read from views.
- **Versioned nonce**, salt fetched from `current_salt`. Salt can rotate.
- **A `sell_note` order can be impossible to fill exactly.** A fill turns the bid's principal into note value at the fill rate (rounded down), then into shares (rounded down), so some share counts are reached by no principal. Example at 8% APR with 21 days left and `V / S = 1`: principal 217 buys 217 shares and 218 buys 219, so 218 is never hit. A fill above the ask's remaining shares is skipped (`ask_oversize`). The matcher sizes each `sell_note` fill as the largest principal whose shares stay within `remaining`, and stops matching an order once no principal fits. The leftover (about 1 unit) stays locked in the order until the owner cancels it, which unlocks and nets it as usual.
- **Set `min_gas` on every intent that calls Setllend.** `intents.near` guarantees only `min_gas` to `on_auth` (default 10 Tgas) and `mt_on_transfer` (default 30 Tgas); anything more is a share of leftover gas. Payouts reserve 15 Tgas and the oracle round trip about 30 Tgas, so the relayer sets `min_gas` to 100 Tgas on every `auth_call`, and the keeper does the same on `liquidate` transfers ([risk-params.md](risk-params.md)). Too little gas fails the call before any state change, so funds are safe, but the action doesn't happen.
- **Indexing events:** read logs only from receipts with a success status, because a receipt that panics can still list the logs it wrote before the panic ⚠️ ([intents-primitives.md](intents-primitives.md#payload-format)). Don't build the book from event amounts: `order_filled` has no escrow left per token, so the `borrow` collateral would have to be recomputed with the contract's rounding and every event applied exactly once. The backend reloads a maturity from views at the height of each block with an event for it instead; a view at block `H` already includes the receipts executed in block `H` ✅ 2026-11-03 ([backend.md](backend.md#book)).
- **The keeper mirrors two valuations.** Liquidatable uses the conservative health factor (`price − conf` for collateral, `price + conf` for debt), but seized collateral is computed at the mid price (D39). The keeper checks liquidatable with the first and estimates its profit with the second, using the same validated oracle prices as the contract.
- **Normalize `v`** of EVM wallet signatures to {0, 1}. Wallets differ (27/28 vs 0/1), so test with at least MetaMask and Rabby.
- **Relayer pays gas:** protect our relayer endpoint from request floods (infrastructure protection, not a user limit: anyone can submit `execute_intents` directly). Use a function-call access key restricted to specific methods. Behind Railway's proxy, rate-limit by the proxy-appended `X-Forwarded-For` entry, not the socket address, or the limit becomes global.
- **A key that signs intents can empty the Intents balance it signs for.** The keeper's NEP-413 key is separate from the gas keys, and the backend's Intents balance is treated as a hot wallet: small keeper capital, seized collateral moved out by hand (D43).
- **The signed JSON must be byte-identical** between frontend and backend. Copy shared types, don't retype them. See [repo-structure.md](repo-structure.md).
- **Matcher and relayer hosting** must stay up until 2026-11-25.
- **Market-maker base rate manipulation (D35):** the agent's base follows fill rates, and EVM accounts are free, so an attacker can fill a dust order between two of their own accounts at an extreme rate to drag the base, then trade against the agent. The contract only blocks same-owner fills. Inside the agent, weight each base move by fill size and bound the move per fill. These are agent settings, not user limits (D24).
- **`lightweight-charts` attribution:** its Apache-2.0 NOTICE requires a link to tradingview.com on the page. Keep the `attributionLogo` chart option on (the default).
- **1Click can pause with short notice, and longer than announced.** On 2026-11-02 a maintenance window announced as about 1 to 2 hours made every `/v0/quote` fail with 400 "Quoting for this pair is not available", then Cloudflare 521. It lasted more than 3 hours and had recovered by the next morning (UTC). The UI must show this as "1Click temporarily unavailable", and the README's "do X, see Y" steps need a path that works without a live 1Click quote. On-chain actions (orders, cancel, repay, withdraw to the Intents balance) don't depend on 1Click.
- **1Click wants Intents accounts in lowercase.** The user's Intents account is the lowercase implicit Eth account (`0x…`). A checksummed (mixed-case) EVM address is rejected with 400 in two places ✅ 2026-11-03: as `recipient` when `recipientType` is `INTENTS` ("recipient is not valid"), and as `refundTo` when `depositType` is `INTENTS`, whatever the `refundType` ("refundTo is not valid"). A checksummed address is accepted where it is an EVM chain address (`refundTo` of an `ORIGIN_CHAIN` deposit, `recipient` of a `DESTINATION_CHAIN` payout). Wallets return checksummed addresses, so lowercase the account before using it on the Intents side.
- **No secrets in git history.** The repo is public from the first commit. Secrets go in `.env` (gitignored) or the hosting dashboard.
